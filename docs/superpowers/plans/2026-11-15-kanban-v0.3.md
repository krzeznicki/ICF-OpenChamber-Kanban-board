# Kanban Board 0.3 — feedback round 2

> Executed with superpowers:subagent-driven-development. Earlier spec and the 0.2 plan stay binding where not changed here. Source: Kamil's second round of feedback.

**Goal:** Agent and thinking level picked from lists, State/Type/Move to above the task text, preset sets (Matt / Superpowers / Plain / custom) chosen per project, and type/state of manually added tasks suggested by the small model.

## Global Constraints

- All 0.2 constraints hold (id `icf-kanban`, sandboxed panel, Matt's repo format, In Progress / Review never in the repo, all git/gh/opencode calls through `Exec`, `npm run check` green, bundles committed, check-guest "Package is ready", UI text in English, untrusted text never executable).
- Facts found (do not re-derive): the SDK gives extensions no model, agent or decision-model API, and no OpenChamber "Auto"/favourites list. `host.generate` is the user's Small Model only. OpenCode's server is reachable with `opencode api GET <path>` (already-permitted `opencode` program): `/api/model` → `{data:[{id, name, providerID, variants:[{id}], …}]}` (398 models here; `variants` are the thinking levels, e.g. low/medium/high/xhigh/max), `/api/agent` → `{data:[{id, name, mode:'primary'|'subagent', hidden, description}]}` (session agents = mode primary and not hidden: build, plan here). Path A (`host.startSession`) cannot set model, agent or variant — it uses OpenChamber's current composer selection; path B (`sessions.start`) takes `model`, `agent`, `variant`.

Any of model, agent or thinking set → path B (as today for model/agent), which passes `variant` to `sessions.start`. Show one muted line under the start options explaining that a set model/agent/thinking starts the session from the extension with its own worktree.

### Task 3: Preset sets

Kamil: "can presets also use Superpowers skills like Matt's? If so: default preset sets — with Matt, with Superpowers, without skill sets — plus user-added custom sets; the set picked per project from a dropdown; presets still editable."

- A **preset set** is a named list of presets. Built-in sets: `matt` ("Matt Pocock's skills"), `superpowers` ("Superpowers"), `plain` ("Plain", no skill set). Users can add a custom set (copy of an existing set or empty), rename, delete; edit any preset in any set; reset an edited built-in preset.
- Set choice: global default in Settings (default: `matt` if its skills are found, else `superpowers` if found, else `plain`) and a per-project override (dropdown in This project). Replaces the 0.2 "Use Matt Pocock's skills when installed" toggle (migrate: toggle off → global default `plain`).
- Preset ids stay stable across sets (plan, prototype, implement, implement-no-questions, orchestrate, diagnose, triage) so `presetByType` and card choices keep working; a set may omit a preset (fall back to `implement`, as today for unknown ids).
- Matt set = the 0.2 mattText presets. Plain set = the 0.2 plain texts. Superpowers set (read each SKILL.md in the superpowers plugin before writing): Plan → `brainstorming` then `writing-plans`; Prototype → `brainstorming` for the question, throwaway code on a `prototype/<name>` branch, answer recorded on the task; Implement → `test-driven-development`, `verification-before-completion`, `requesting-code-review`; Implement without questions → same, deciding unclear points and listing assumptions; Orchestrate → `writing-plans` if no sub-tasks, then `subagent-driven-development` over the sub-tasks; Diagnose → `systematic-debugging` then TDD fix; Triage → plain triage text. Every text keeps the 0.2 rules: tracker writes through the task-board CLI with `--dir`, placeholders quoted, the board's worktree already exists (don't create another), never run setup skills.
- Detection: add the superpowers skill names; besides the skill folders, look in OpenCode's plugin cache `~/.cache/opencode/npm/*/*/node_modules/superpowers/skills/<name>/SKILL.md` (glob, read-only). Settings shows which sets are available; an unavailable set can still be chosen, with a warning.
- Storage: sets and edits in extension storage; parse defensively; old `presets` key migrated.
- Tests: set resolution (global/project), migration, preset lookup in a set, detection incl. plugin cache.

### Task 4: Type and state suggested by the small model

Kamil: "can extension features use OpenChamber's decision model? If so, to set type and state of manually added tasks; if not, use the small model when doing the summary, and set those fields only if they weren't set while adding."

- The SDK has no decision-model access, so use `host.generate` (Small Model).
- Add-task modal: Type and State get a first option "Let the model pick" (the default). When either is left on it, after the task is created the panel asks the small model once for `{type, state}` (JSON; type from the board's types, state from needs-triage / needs-info / ready-for-agent / ready-for-human), validates the answer, and applies only the fields the user left on "Let the model pick" with setType / setState. Until then the task is needs-triage with no type. Run it alongside the summary request (same concurrency limit), not as part of the summary cache.
- NO_MODEL / failure / invalid answer → leave the defaults, one quiet notice per panel session. Never touch tasks created elsewhere (CLI, agents, GitHub).
- A setting "Suggest type and state for new tasks" (global, default on).
- Tests: prompt building, answer parsing/validation, which fields get applied.
